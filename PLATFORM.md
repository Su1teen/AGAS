# AGAS: маркетплейс и кабинет поставщика

## Архитектура

Оба интерфейса используют единый API из `server/` в AGAS. Это отдельный процесс Node.js 24, Express и SQLite (WAL, внешние ключи, транзакции). Интерфейсы остаются TanStack Start / React, со своими текущими сборками Cloudflare. Сервер SQLite нельзя запускать внутри Cloudflare Worker или на непостоянной файловой системе Vercel.

Существовавшие проекты содержали статический каталог и интерфейс кабинета без общей БД. PayPal удалён. Исходный каталог из 77 позиций перенесён в серверный seed; существующие ссылки, корзина и изображения сохранены. Импортированные товары получают постоянные ID и доступны в общем каталоге, карточке, корзине и checkout.

В Navigator сохранены светлое оформление, верхняя навигация и карточки исходного проекта. Русский включён по умолчанию; RU/EN и KZT/USD доступны в обеих платформах. Курс USD берётся сервером из официального RSS НБК, кэшируется на час, содержит дату и источник. При сбое курс не выдумывается. Расчёт USD справочный; цены хранения, импорт и счета всегда в KZT. Перевод относится к интерфейсу, а не к пользовательским названиям и документам поставщиков.

## Локальный запуск

1. Установить Node.js 24, выполнить `npm ci` в AGAS и `npm ci --legacy-peer-deps` в agas-navigator.
2. Скопировать `.env.example` в `.env` в каждом репозитории. В AGAS заполнить настоящие реквизиты продавца. Не использовать тестовые реквизиты из автоматических проверок.
3. В AGAS выполнить `npm run seed:catalog` при изменении исходного статического каталога и `npm run api` для API на порту 4000.
4. В AGAS запустить `npm run dev -- --port 3000`, в Navigator — `npm run dev -- --port 3001`.
5. Создать аккаунт поставщика в Navigator. Его роль — владелец собственной компании. Другие компании изолированы. Редактор и аналитик добавляются владельцем в настройках команды.

Первый запуск API применяет `server/migrations/001-platform.sql`. Повторный запуск безопасен. SQLite и все версии PDF находятся в `server/data/agas.sqlite`, каталог данных исключён из Git. Создавайте согласованные резервные копии SQLite, включая WAL, средствами SQLite; не копируйте только открытый основной файл БД.

## Счета и гостевой checkout

Гость может сформировать счёт без регистрации. Создаётся случайная защищённая сессия текущего браузера; доступ к PDF проверяется по ней. Срок сессии — 7 дней. Гостевой PDF следует скачать или отправить по email: восстановление гостевого доступа без cookie не реализовано. Зарегистрированные пользователи видят счета своего аккаунта. Email сам по себе не предоставляет доступ к документу.

Сервер принимает ID и количество товаров, заново проверяет наличие и рассчитывает суммы целыми тиынами. Пользователь не может передать цену или назначить заказу статус «оплачен». Номер счёта последовательный, выдаётся SQLite AUTOINCREMENT; возможные пропуски не переиспользуются. Снимок реквизитов, строк, суммы и условий сохраняется вместе с заказом. PDF v1 хранится в БД с SHA-256, доступен для просмотра, загрузки и печати. Повторный запрос с тем же ключом и данными возвращает тот же счёт. Браузер сохраняет ключ незавершённого запроса с хешем данных в sessionStorage.

НДС не придуман: пустой `SELLER_VAT_RATE` означает «не указан продавцом», 0 — явно нулевая ставка. Настроенная ставка начисляется сверх цен товаров; доставка задаётся целыми тиынами в `DELIVERY_MINOR`. Требуется подтвердить эти условия перед использованием. Без корректных реквизитов продавца выставление счёта блокируется. Счёт не является ЭСФ, не содержит поддельных подписей и печатей. Выпуск счёта не резервирует остаток и не подтверждает банковский платёж.

`SMTP_URL` и `MAIL_FROM` включают отправку PDF через Nodemailer. Без настроенного провайдера кнопка отправки недоступна, скачивание работает. Успех показывается после принятия письма почтовым провайдером; это не доказательство доставки в ящик. Настоящая почта в ходе разработки не отправлялась.

## Импорт и экспорт

XLSX и CSV UTF-8: до 10 МБ, 5000 строк, 80 колонок. XLSX проверяется до распаковки: не более 50 МБ содержимого и 3000 ZIP-объектов. Можно выбрать лист, переназначать поля и пропускать колонки. Цены с запятой и пробелами распознаются, пустые и некорректные числа отклоняются. Обязательны артикул, название, категория, цена и остаток.

Ключ upsert — supplier + нормализованный SKU. Повторные SKU внутри файла выделяются как ошибки. По умолчанию ошибочный файл не публикуется; пользователь может явно сохранить только корректные строки. Публикация атомарна и идемпотентна для одного импорта. Сохраняются история и XLSX-отчёт каждой строки; сырые данные после подтверждения очищаются, неоконченные загрузки истекают через сутки. Повторный импорт публикует обновлённые позиции.

Фото: HTTPS URL, гиперссылка ячейки или одно встроенное PNG/JPEG/WebP на строку, привязанное верхним левым углом к строке товара. До 2 МБ на фото, до 8 МБ суммарно. URL имеет приоритет. Формулы IMAGE, макросы, внешние связи книги, SVG, старый XLS и неподдерживаемые объекты не импортируются. Сервер не скачивает внешние URL. ISO, ссылка на сертификат и номер документа сохраняются как метаданные без подтверждения их подлинности. Подписи/печати не создаются. Экспорт каталога не включает бинарные встроенные фото; это явно отмечается в ячейке. XLSX-экспорт содержит оформление, фильтр и закреплённый заголовок; потенциальные формулы из пользовательских строк экранируются.

## Права и безопасность

Пароли хешируются scrypt с индивидуальной солью. Сессии случайные, в БД хранятся их хеши; cookies HttpOnly, SameSite=Lax и Secure в production. Изменяющие запросы требуют разрешённый Origin. CORS задаётся `ALLOWED_ORIGINS`, включены Helmet и ограничения частоты запросов. SQL-запросы параметризованы. Поставщик видит только свои товары, загрузки, контакты и строки заказов; полный PDF покупателя ему не передаётся. Аналитик не может редактировать данные; управление командой доступно только владельцу.

## Проверки

`npm run lint`, `npm run typecheck`, `npm test`, `npm run build`. Серверные проверки включают XLSX с 120 товарами, встроенным фото, URL и несколькими листами; CSV с ошибками и дублями; импорт/upsert 120 товаров; права и изоляцию; серверные суммы; повтор счёта; защищённый PDF; сохранность после перезапуска; экспорт и CSRF. Браузерный тест `npm run test:e2e` в AGAS использует оба запущенных интерфейса и изолированный backend `node tests/e2e-server.mjs`. Он проверяет импорт 110 товаров, маппинг, экспорт, гостевой checkout, PDF, CRM, RU/EN, валюты, мобильную ширину и ошибки соединения. Проверки используют отдельные тестовые данные.

## Развёртывание и ограничения

API необходимо разместить отдельно на сервере Node.js 24 с постоянным диском. В production `VITE_AGAS_API_URL` должен указывать на API; без переменной интерфейс использует `/api` своего origin, для которого требуется reverse proxy. Обе платформы и API должны использовать HTTPS и совместимые сайты для SameSite-cookie, например поддомены одного домена. Настроить origin, резервные копии, почту, реальные банковские реквизиты, доставку и НДС. В текущем репозитории нет инфраструктуры для их автоматического развёртывания.

Перед публичным запуском дополнительно нужны подтверждение email, восстановление/смена пароля, управление сроками хранения персональных данных, отзыв доступа сотрудников, модерация новых поставщиков, резервирование склада, подтверждение платежей и интеграция ЭСФ при необходимости. Локальная SQLite предназначена для одного экземпляра API; для горизонтального масштабирования нужна общая транзакционная БД и объектное хранилище. Перевод введённых пользователями описаний не выполняется автоматически.

Сетевой npm audit в локальном окружении возвращал timeout / HTTP 503 от сервиса npm. Это не подтверждение отсутствия уязвимостей. В GitHub Actions добавлена повторная проверка с порогом high; при её ошибке слияние требует устранения причины.

Исторические slug товаров и ключи корзины с прежним префиксом сохранены для совместимости; видимый бренд заменён на AGAS. Начальный каталог переносит исходный признак наличия; лимит 999 для этих позиций не является подтверждённым складским остатком. Перед реальным использованием загрузите фактические остатки.

## Cloudflare Workers Builds

Локальные проверки и GitHub Actions используют актуальный package-lock.json и npm. Cloudflare использует Bun с bun.lock и защитой minimumReleaseAge=86400; lockfile должен соответствовать package.json. .npmrc сохраняет совместимость установки npm с более поздней prerelease-версией Nitro. Node.js 24 закреплён в .node-version и .nvmrc. Команда сборки: `npm run build`. Команда публикации: `npm run deploy` (или `npx wrangler deploy`). Nitro явно создаёт `dist/server/wrangler.json` и `dist/client`, сохраняя пути прежней конфигурации. `npm run deploy:check` проверяет упаковку без публикации. Старую явно заданную команду, ссылающуюся на иной путь, необходимо заменить в Cloudflare.

Успешные GitHub checks не означают успешный деплой Cloudflare: проверять отдельно Workers Builds и опубликованный домен. Backend из server/ по-прежнему требует отдельного Node.js сервера с постоянным диском; Worker публикует интерфейс и не запускает SQLite API.
